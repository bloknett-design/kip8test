### Главная находка: дыра двойного submit в verifyOTP

Замок Task 348 оберегал мутации, но **OTP читался ДО замка**:
два параллельных submit ОДНОГО кода оба видели «unused» (внешнее
чтение), второй входил в замок после первого, помечал код used
повторно и **создавал ВТОРУЮ сессию с одного кода** — двойной вход
не блокировался, вопреки замыслу Task 348.

**Стало:** `getActiveOtpForEmail` вызывается ТОЛЬКО внутри замка
(пере-чтение). Второй submit видит «used» и получает
«Код не найден или истёк». Сессия с одного кода — ровно одна.

Попутно добавлены гарды (раньше были бы TypeError/краш):
- юзер удалён между пред-проверкой и замком в verifyOTP →
  штатное «Неверный код» + аудит;
- юзер удалён между пред-проверкой и замком в sendOTP →
  тихий «код отправлен» без письма + аудит.

Аудит успешного входа (`OTP_VERIFIED`, `LOGIN_SUCCESS`)
перенесён ВНУТРИ замка: `appendRow` дописывает в конец листа и
НЕ сдвигает чужие строки — гонки нет, а throw-пути (неверный код,
истечение, Запрет) остаются с корректным аудитом.

## Пункт 2. Батч-удаления чисток

**Диагноз:** `audit_log` (90 дней истории) и `otp_codes` —
append-only листы (записи только дописываются в конец), поэтому
просроченные строки = сплошной блок СВЕРХУ (данные с r5). Старый
код вызывал `deleteRow` на КАЖДУЮ строку — сотни последовательных
API-вызовов, риск упереться в 6-минутный лимит триггера.

| Чистка | Было | Стало |
|---|---|---|
| `cleanupOldAuditLogs` | deleteRow × N (сотни вызовов) | один `deleteRows(5, N)` + страховочный проход с конца |
| `cleanupExpiredOtpCodes` | deleteRow × N | один `deleteRows(5, N)` + страховка |
| `cleanupExpiredSessions` | `findUserById` на КАЖДУЮ строку sessions (каждый вызов = полный перечит листа users, O(n²) чтений) | users читается ОДИН раз → индекс живых ID |

**Страховочный проход** нужен для строк, выбившихся из хронологии
(ручная вставка в середину листа): после батча их номера сдвинуты
на N вверх → `row - prefix`, удаление с конца (номера ниже не
съезжают). В нормальном листе страховка находит 0 строк.

**Семантика чисток НЕ менялась:**
- сессии бессрочные, удаляются только сироты (юзер удалён) и
  «заброшенные» (STALE_SESSION_DAYS, Task 347);
- легаси-строки sessions без `user_id` — сироты, как и раньше;
- строки с не-Date датами (повреждённые) НЕ удаляются, как и раньше;
- имена событий аудита не менялись (`SESSION_CLEANUP_ORPHAN`,
  `SESSION_CLEANUP_STALE`); чистки теперь ВОЗВРАЩАЮТ число
  удалённых строк (hourlyCleanup его игнорирует — это для
  логирования/отладки).
