## Пункт 1. Admin.deleteUser (аудит п.3)

**Диагноз:** удалить пользователя можно было только руками из
листа `users`. Хвосты: сессии висели «сиротами» до ближайшего
hourlyCleanup, а АКТИВНЫЙ OTP оставался годен до конца TTL —
если юзера с той же почтой сразу пересоздать, старый код пускал
«нового» юзера на вход.

**Новая функция** (`Utils.gs`, объект `Admin`; роут в `Code.gs` —
`action=adminDeleteUser`, гейт `admin.panel` как у остальных
админ-действий). Всё под `Utils.withLock` (паттерн resetLogin):

| Шаг | Что делает |
|---|---|
| гарды | юзер не найден → `User not found`; `Number(user.ID) === Number(admin.ID)` → «Нельзя удалить собственный аккаунт»; жертва-админ без других админ-строк → «Нельзя удалить последнего администратора» |
| 1 | сессии юзера — с конца, по `user_id` **ИЛИ** `email` (легаси Task 37 с пустым user_id) |
| 2 | OTP-строки по `email` (активный код умирает вместе с юзером) |
| 3 | строка `users` — ПОСЛЕДНЕЙ (удаления в других листах не сдвигают нумерацию users; `user.row` собран под замком) |
| 4 | аудит `ADMIN_DELETE_USER` с деталями (email, id, сколько сессий/OTP снесено) |

Ответ: `{ ok: true, deleted: <email>, sessionsRemoved: N,
otpsRemoved: M }`.

**UI в админ-панели НЕТ** (в аудите заявки не было) — функция
вызывается напрямую POST `?action=adminDeleteUser` с телом
`{"token": "...", "userId": N}`. Кнопку в админке можно добавить
отдельной задачей: подойдёт обычный confirm-диалог, сервер
сам защитит от ошибок (гарды).

## Пункт 2. Кэш чтений на одно выполнение (аудит п.4)

**Диагноз:** `Utils.getRows(name)` каждый раз делал полный
`getRange().getValues()`. Внутри ОДНОГО запроса лист читался
по несколько раз: `sendOTP` — users ×2, config ×5-6 (каждый
`getConfig` = полный перечит!), audit_log ×2; гейтированные
админ-действия — гейт (`rmRequirePerm`) + модуль читали
sessions и users ПО ДВАЖДЫ каждый; `adminListLogs` — 4 полных
чтения users/sessions + весь audit_log.

**Стало:** `Utils._rowsCache` — кэш на СТРОГО одно выполнение:

| Механизм | Где |
|---|---|
| `Utils.beginExecution()` — сброс кэша в начале каждого входа | вызывается первой строкой в `doPost` и `hourlyCleanup` (`Code.gs`) |
| `Utils.getRows(name)` — повторное чтение того же листа = ОДИН API-вызов | возвращает `.slice()`-копию: сортировка ответа (listLogs) не портит кэш; объекты строк общие — поля только читать |
| инвалидация при ЛЮБОЙ записи | встроена в `appendRow`, `deleteRow`, НОВЫЙ `deleteRows` (батч), `setCell`, `updateUserStatus`, `markOtpUsed`, `incrementOtpAttempts`, `audit` (через appendRow) |
| прямые записи переведены на хелперы | `updateRole`: users!C и sessions!D → `Utils.setCell`; батчи чисток → `Utils.deleteRows`; `Sessions.gs`: heartbeat (sessions!F) и getCurrentUser (sessions!D) → `Utils.setCell` |

**Почему сброс именно в doPost/hourlyCleanup:** GAS МОЖЕТ
переиспользовать глобальное состояние между выполнениями на
одном инстансе — без сброса второй запрос получил бы снапшот
листов первого (устаревшие строки → ложные session_expired).
Это единственные входы продакшена: все HTTP-запросы идут через
`doPost`, крон — `hourlyCleanup`.

Эффект (полные чтения API за запрос):
- `sendOTP`: ~6-8 → **4** (users, audit_log, otp_codes, config);
- `verifyOTP`: ~5-6 → **4** (users, otp_codes, sessions, config);
- админ-гейтованные действия: 4 чтения users/sessions → **2**;
- `getCurrentUser`/`heartbeat`: 2 → 2 (листы разные, повтора нет —
  но записи больше не оставляют устаревший кэш).

## Пункт 3. listLogs — хвост audit_log

**Было:** `getRows('audit_log')` — ВЕСЬ лист (90 дней × сотни
событий/день = десятки тысяч строк × 6 колонок), потом полная
сортировка и `slice(0, limit)`.

**Стало:** новый `Utils.getLastRows(name, count)` — два маленьких
чтения: заголовки (r4) + последние `count` строк. Лист
append-only (Task 350) → свежие события физически внизу →
«последние N» = хвост. Хвост ещё сортируется по убыванию
timestamp — страховка от нехронологических вставок.
Лимит-кламп прежний: `Math.min(limit || 100, 500)`.

## Пункт 4. Устойчивый getConfig (аудит п.6)

**Диагноз:** числовая настройка проходила как есть: `''` →
`'' * N = 0` → cutoff «сейчас» → `cleanupStaleSessions` сносила
бы ВСЕ сессии; `'abc'` → NaN → чистки молча не работали; `'0'` /
`'-5'` — опасные пороги.

**Стало:** если у `getConfig(key, defaultValue)` дефолт — ЧИСЛО,
значение парсится мягко (`trim` + `parseInt`: `'30 дней'` → 30,
`' 30 '` → 30), а при NaN или `< 1` возвращается дефолт +
`console.warn` (видно в логах). Все 9 числовых ключей
(STALE_SESSION_DAYS, AUDIT_LOG_RETENTION_DAYS, OTP-лимиты,
SESSION_TOKEN_LENGTH…) имеют смысл только ≥ 1. Строковые ключи
(SUPPORT_REPLY_TO) — прежнее поведение. Отдельный getConfigInt
НЕ вводился: тип дефолта решает, все существующие вызовы уже
передают числа.

## Проверка после деплоя

1. **Вход работает**: код → письмо → ввод → токен (кэш прозрачен).
2. **Сессия живёт**: пара запросов heartbeat подряд — `{ok:true}`;

   как раньше (порядок — новые сверху).

   `POST ...?action=adminDeleteUser {"token":"...","userId":N}`
   → `{ok:true, data:{ok:true, deleted:"...", sessionsRemoved:N,
   otpsRemoved:M}}`; жертва выбрасывается на ближайшем heartbeat
   (session_expired); повторный вызов → `User not found`.
   Удаление самого себя → «Нельзя удалить собственный аккаунт».
5. **Кэш не врёт**: смена роли админом видна жертве сразу
   (getCurrentUser перечитывает — invalidateCache от setCell);
   logout → вход работает.
6. **Конфиг-мусор**: временно записать в config
   `STALE_SESSION_DAYS` = `abc` → в логах warn «использую
   дефолт 30», чистка работает как при 30 (вернуть значение!).
