# Task 420 — DEPLOY: нестрогая связь 9-ОГЭ и полный цикл «по кругу»

Заявка: «я сделал отметку о выполнении общего инструктажа, а создалась
только одна новая запись о следующем общем инструктаже (должна появиться
запись о 9-ОГЭ через три месяца».

## Диагноз

Встроенная связь 9-ОГЭ → общий (`INSTR_DEFAULT_PARENT`, Task 419)
применялась ТОЛЬКО при точном совпадении названия пункта с эталоном
«Повторный инструктаж по инструкции № 9-ОГЭ». Фактические названия
в живом листе «Список_И_и_ПЗ» отличаются («№», «Повторный», тире,
регистр) → у отметки общего инструктажа детей не находилось →
создавалась только запись общего +6 мес, запись 9-ОГЭ +3 мес не
появлялась.

Дополнительно найден пробел цикла: отметка самостоятельного 9-ОГЭ
(когда общий в окне отсутствует) создавала ещё один 9-ОГЭ +3 мес —
цикл мог деградировать в цепочку «только 9-ОГЭ» без общего.

## Что сделано (SW kipia-test-v647)

### Сервер `scripts/WorkSchedule.gs`

1. **Нестрогие сравнения** (Task 420):
   - `_sigKey(name)` — сигнатура названия: только буквы и цифры,
     слитно («№ 9-ОГЭ» / «9-ОГЭ» / «9 – ОГЭ» / «9‑ОГЭ» → «9огэ»);
   - `_sameInstrName(a, b)` — равенство норм-ключом ИЛИ сигнатурой:
     тема записи ↔ название пункта ↔ связь «в составе» больше
     не ломаются из-за «№», тире, точек и регистра.
2. **Встроенная связь ищется нестрого** (`_readInstrListSheet`):
   - ребёнок: точное совпадение с эталоном ИЛИ сигнатура содержит
     «9огэ»;
   - родитель: цепочка эталон → сигнатура содержит
     «рабочиминструкциям» → «общий» + вид не «проверка_знаний»;
   - связь записывается НАЗВАНИЕМ пункта листа (совпадает с темами
     его записей);
   - заполненный столбец «в составе» главнее, но значение, не
     совпадающее ни с одним пунктом листа, для 9-ОГЭ замещается
     встроенной связью (спасение от опечаток ручного заполнения);
   - инверсия (родитель «в составе» ребёнка) стирается;
   - **пустая периодичность 9-ОГЭ → 3 мес** (эталон заявки:
     «период 3 месяца»).
3. **Цикл «по кругу» — правило (0)** (`_autoCreateNextTrainings`):
   отметка РЕБЁНКА (без его собственных детей) → создаётся
   РОДИТЕЛЬ на дата + N(ребёнка): после самостоятельного 9-ОГЭ через
   3 мес идёт общий инструктаж. Родитель создаётся РАНЬШЕ
   собственного срока пункта — его запись в окне (дата; дата+N]
   закрывает отдельную запись ребёнка, чередование 3/6 мес не
   деградирует. Если общий в окне уже есть (штатный случай) —
   ничего не создаётся, дублей нет.
4. Аудит `WORKSCHEDULE_SET_TRAINING_DONE` несёт разбор
   соответствия: `[пункт=… родитель=… дети=…]` — по нему видно,
   почему создано именно так (журнал Apps Script, Ctrl+Enter).

### Клиент `index.html`

1. `_normalizeInstrList` — встроенная связь 9-ОГЭ строится и на
   КЛИЕНТЕ для живого списка без «в составе» (старый Apps Script /
   кэш): те же сигнатуры, период 3 при пустой ячейке. «след. срок»
   9-ОГЭ (+3 мес от общего) показывается сразу, до обновления
   сервера.
2. `_renderInstrSection` — «последнее» событие пункта сравнивается
   с ключами нестрого (сигнатура) — записи с «№»/тире не выпадают.

## ⚠ СЕРВЕРНЫЙ ШАГ (обязательно)

Автосоздание записей 9-ОГЭ работает только после обновления
сервера:

1. Открыть проект Apps Script табель_КИП_ИОС;
2. заменить содержимое `WorkSchedule.gs` на новый
   `scripts/WorkSchedule.gs` из репозитория (main, коммит Task 420);
3. **Создать НОВУЮ ВЕРСИЮ развёртывания** (Deploy → Manage
   deployments → Edit → New version), старую версию не трогать;
4. Code.gs и маршрут не менялись; `instrListInit` запускать НЕ нужно
   (связь встроенная; столбец «в составе» остаётся опциональным).

До обновления сервера клиент уже показывает «след. срок» 9-ОГЭ
корректно (клиентская связь), но отметка общего по-прежнему создаст
только одну запись (старый сервер).
