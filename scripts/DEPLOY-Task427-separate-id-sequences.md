# Task 427 — раздельные последовательности id «Инструктажей» и «Мероприятий»

**Заявка (kip8test):** «При создании новых строк в таблицах
Инструктажи и Мероприятия, столбец id в них заполняется общей
последовательностью по нарастанию значений, нарастание номеров id в
них должно быть раздельным, значит где то в коде эти разделы до сих
пор перекликаются. Проверь, исправь, должно быть полное разделение
между разделами инструктажей и мероприятий, в том числе формирование
порядковых номеров id новых строк в таблицах».

## Диагноз (где разделы «перекликались»)

Разделение таблиц было сделано в Task 405, но id остался **сквозным
по обоим листам**: `addTraining` и `_autoCreateNextTrainings` брали
максимум id по **ОБОИМ** листам (`max(«Инструктажей»,
«Мероприятий») + 1`) — новая запись «Мероприятий» получала номер
после самого большого id «Инструктажей» (и наоборот). Это и выглядело
как «общая последовательность по нарастанию».

## Что изменилось

**Сервер `scripts/WorkSchedule.gs`:**

1. **`addTraining`: id = максимум СВОЕГО листа + 1** (главное,
   заявка): маршрутизация по типу уже определяет лист записи —
   теперь и нумерация своя у каждого листа. Сквозной кросс-максимум
   удалён. Существующие строки НЕ перенумеровываются (id в
   «Инструктажах» продолжаются от своего максимума, id в
   «Мероприятиях» — от своего).

2. **`_autoCreateNextTrainings`: нумерация только «Инструктажей»** —
   автосоздание пишет исключительно в лист «Инструктажей», максимум
   «Мероприятий» больше не участвует. Правила автосоздания
   инструктажей **не тронуты** (Task 419..423: общий → 9-ОГЭ +3 мес
   эталона + общий +6 мес; отметка 9-ОГЭ — только фиксация;
   стоп-правило мероприятий Task 425 живо — регресс покрыт
   тестами).

3. **`deleteTraining`: адресация «id + семейство типа»** — у листов
   раздельные последовательности, значит **одинаковый id может
   лежать в обоих листах**. Клиент передаёт флаг `инстр` (1 —
   инструктаж/проверка_знаний, 0 — обучение/прогул/примечание):
   сервер ищет строку с id И типом того же семейства, семейство —
   свой лист первым (легаси-мероприятия в «Инструктажах» Task 425
   удаляются так же — по типу строки, столбец C). Без флага (старый
   кэш клиента) — прежний порядок «Инструктажи» → «Мероприятия».

4. `srvVer` '426' → **'427'**.

**Клиент `index.html`:**

1. **Кнопки ✎/✕ (попап дня, блоки карточки, группы шаблона,
   «вне списка») передают семейство записи** — правка/удаление
   адресуют id в СВОЕМ разделе; подтверждение удаления показывает
   раздел («Удалить запись id=N (мероприятие)?»).
2. **`editTraining(id, fam)`** — поиск записи по id + семейство
   (запись чужого раздела с тем же id не перехватывается).
3. **`toggleTrainingDone`** — галочка ищет и обновляет **только
   записи инструктажей** (копии мероприятий с тем же id не
   помечаются).
4. **`_wtabYearRecords`** — ключ дедупа по семейству типа
   (`'i'+id` / `'e'+id`): одинаковые id инструктажа и мероприятия —
   **ДВЕ записи** в карточке (раньше одна «съедалась»).
5. **Правка (add новой + delete старой)** передаёт семейство ИСХОДНОЙ
   записи (`инстр: oldFam`) — тип в правке может смениться на другой
   внутри того же семейства.
6. **Порог предупреждения «старый сервер»**: `srvVer < 427` —
   сервер с сквозной нумерацией id тоже считается старым
   (предупреждение в тосте отметки инструктажа; историческая граница
   423 — период 9-ОГЭ — поглощена).

## Деплой

1. **GitHub**: push в `main` (CI зелёный).
2. **Пользователь (сервер)**: заменить `WorkSchedule.gs` в редакторе
   Apps Script → **Создать новую версию развёртывания**.
3. Клиент обновится сам (SW `kipia-test-v654`).

## Самопроверка после деплоя

1. Добавить новое мероприятие → id = последний id **листа
   «Мероприятия»** + 1 (НЕ после самого большого id «Инструктажей»).
2. Добавить/отметить инструктаж → новый id продолжает
   **«Инструктажи»** (автосоздание отметкой общего — тоже).
3. Удаление мероприятия с id, совпадающим с id какого-нибудь
   инструктажа, удаляет именно мероприятие (и наоборот).
4. В тосте отметки инструктажа НЕТ предупреждения «⚠ Сервер Apps
   Script старой версии…» (srvVer 427).
