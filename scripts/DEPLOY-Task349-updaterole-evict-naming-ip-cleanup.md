## Пункт 1. Мёртвый IP-код удалён (вариант А — удалить)

**Диагноз:** Apps Script в `doPost` НЕ видит IP и User-Agent
клиента. Хелперы `Utils.getClientIp()` / `Utils.getClientUserAgent()`
всегда возвращали `''`, поэтому:

- пер-IP ветка sendOTP «20 неудач/час с одного IP» не срабатывала
  НИКОГДА — её счётчик `Utils.countRecentAuditLogsByIp` начинался
  с guard `if (!ip) return 0` и всегда возвращал 0;
- колонки `ip` / `user_agent` в audit_log всегда пустые.

**Удалено:**

| Что | Где | Почему мёртвое |
|---|---|---|
| per-IP ветка «20 неудач/час» | `Auth.sendOTP` | счётчик всегда 0 (ip = `''`) |
| `Utils.getClientIp()` | `Utils.gs` | всегда `''` — IP в GAS недоступен |
| `Utils.getClientUserAgent()` | `Utils.gs` | всегда `''` |
| `Utils.countRecentAuditLogsByIp()` | `Utils.gs` | вызывался только из мёртвой ветки |
| локальные `ip`/`ua` в sendOTP/verifyOTP | `Auth.gs` | источники удалены |
| конфиг-ключ `RATE_LIMIT_FAILED_PER_IP` | нигде | никто никогда не задавал |

**Сигнатура `Utils.audit(email, action, ip, ua, details)` НЕ
менялась** (40+ вызовов по всем файлам — трогать рискованно):
3-й и 4-й аргументы теперь буквально `''` в каждом вызове Auth.gs.
Колонки `ip`/`user_agent` в листе audit_log остаются (история), но
всегда пустые — как и были.

**ЖИВАЯ защита сохранена:** глобальный лимит 100 OTP/час
(`RATE_LIMIT_OTP_PER_HOUR`, счётчик `countRecentAuditLogs`) +
`MAX_OTP_ATTEMPTS` (5) с блоком `OTP_BLOCK_MINUTES` (30) +
cooldown 60 сек. Брутфорс конкретного ящика останавливают
попытки+блок, перебор почтовых ящиков — глобальный лимит.

## Пункт 2. Унификация имён SESSION_*

Событие удаления осиротевшей сессии в heartbeat
(`Sessions.gs`) переименовано:

| Старое имя | Новое имя | Где встречается |
|---|---|---|
| `SESSION_ORPHAN_REMOVED` | `SESSION_CLEANUP_ORPHAN` | heartbeat (ленивый путь) |

Крон-путь `Utils.cleanupExpiredSessions` уже писал
`SESSION_CLEANUP_ORPHAN` — теперь ленивый и крон-пути пишут ОДНО И
ТО ЖЕ имя. Все сессионные события — под единым префиксом
`SESSION_CLEANUP_*` (`SESSION_CLEANUP_ORPHAN`,
`SESSION_CLEANUP_STALE` из Task 347).

- Старые записи audit_log НЕ переписываются — история остаётся со
  старым именем (в поиске по audit_log можно искать оба имени).
- `STALE_SESSION_DAYS` (config, заведён руками) НЕ переименовывался.
- Новых типов событий НЕ введено.

## Пункт 3. updateRole: замок + снапшот роли + мгновенная выгонка

**Было (две проблемы):**

1. `sessions!D` — role-снапшот на момент входа. `updateRole` писала
   только `users!C`, снапшот висел со СТАРОЙ ролью до ближайшего
   запроса жертвы (getCurrentUser лениво синхронил). Пользователь
   офлайн — снапшот устаревает бессрочно.
2. «Запрет» срабатывал ТОЛЬКО когда жертва сама делала запрос
   (getCurrentUser/heartbeat). Мгновенной выгонки не было.

**Стало** (всё под `Utils.withLock` — updateRole была последней
мутацией без замка, теперь пишет users!C + строки sessions атомарно
против параллельного heartbeat/logout):

- **обычная роль** — users!C записывается, затем role-снапшот
  `sessions!D` обновляется во ВСЕХ живых сессиях юзера сразу
  (строки с уже актуальной ролью не перезаписываются);
- **«Запрет»** — МГНОВЕННАЯ выгонка в стиле resetLogin: удалить ВСЕ
  строки сессий юзера (с конца — deleteRow сдвигает номера строк) +
  сброс login_status в «вход не выполнен». Роль-снапшоты не
  трогаются — строк больше нет. Клиент жертвы узнает на ближайшем
  запросе: любой вызов с её токеном → `no_session`/`session_expired`
  (heartbeat каждые 5 мин или любое действие — сразу);
- аудит: `ADMIN_UPDATE_ROLE` (с числом вытесненных, «instant evict:
  N session(s)») + существующее `FORCE_LOGOUT_ROLE` от имени жертвы
  — новых типов событий не введено;
- офлайн-жертве (сессий нет) статус не сбрасывается принудительно —
  он и так «вход не выполнен», ложного FORCE_LOGOUT_ROLE нет.

**Чтения внутри замка** (паттерн Task 348): поиск юзера и валидация
роли выполняются после взятия замка — прочитанное снаружи устаревает.

## Проверка после деплоя (~3 минуты)

1. **Вход работает**: запросить OTP, войти — сессия создалась,
   `server_busy` видеть не должны (замок updateRole короткий).
2. **Снапшот роли**: залогиненному юзеру сменить роль на любую
   обычную (например «КИП8 pro») в админ-панели → в листе `sessions`
   колонка D его строк изменилась СРАЗУ (не ждём запроса юзера).
   Жертва может оставаться залогиненной.
3. **Мгновенная выгонка**: сменить роль залогиненного юзера на
   «Запрет» → его строки в `sessions` исчезли сразу, `users!D` =
   «вход не выполнен»; приложение жертвы при любом действии (или
   heartbeat ≤5 мин) уходит на экран входа. Вернуть роль обратно —
   юзер входит заново обычным порядком.
4. **audit_log**: при смене на «Запрет» — `ADMIN_UPDATE_ROLE` с
   «instant evict: N session(s)» и `FORCE_LOGOUT_ROLE`. События
   IP-фильтра не появились (RATE_LIMIT_HIT остаётся только для
   глобального лимита 100/час).
5. **Новое имя сироты** появится в audit_log со временем — при
   первой чистке осиротевшей сессии (heartbeat или cron): строка
   `SESSION_CLEANUP_ORPHAN`. Старые записи `SESSION_ORPHAN_REMOVED`
   в истории не меняются — это нормально.
