# DEPLOY Task 348 — Utilities.getUuid() вместо Math.random + LockService от гонок

**Контекст (09.09.2026, сопровождение Tasks 346/347):** заявка
пользователя — закрыть отложенные улучшения «всё разом»:
1) криптостойкая генерация токенов; 2) сериализация мутаций против
гонок. Порог `STALE_SESSION_DAYS` пользователь уже настроил сам
(лист `config`), эта правка кода его НЕ трогает.

**Зачем getUuid:** `Math.random()` — не криптографический генератор
(последовательность теоретически восстанавливается по нескольким
выданным значениям), а сессии по заявке бессрочные — угаданный токен
жил бы вечно. `Utilities.getUuid()` — встроенный криптостойкий
источник: один UUID минус 4 дефиса = ровно 32 hex-символа (дефолтная
длина токена). OTP-коды (6 цифр) тоже генерируются из getUuid.
**Миграция НЕ нужна:** старые токены остаются валидными, меняется
только генерация новых (charset `[0-9a-f]` вместо `[A-Za-z0-9]`,
длина та же); клиент сравнивает коды как текст — формат OTP не меняется.

**Зачем LockService:** Apps Script обрабатывает запросы ПАРАЛЛЕЛЬНО.
Любая цепочка «прочитал → посчитал → записал» может перемешаться с
чужой такой же. Конкретные гонки, которые закрываем:

| Где | Что было при совпадении по времени |
|---|---|
| `Admin.createUser` | два createUser → оба считают `maxId+1` → **два юзера с одним ID** |
| `Sessions.heartbeat` | чужой deleteRow между чтением и `setValue(session.row, 6)` → **запись в ЧУЖУЮ строку** (номера строк съезжают) |
| `Sessions.logout` | то же + `_userHasOtherSession` по устаревшей раскладке → неверный сброс статуса |
| `Sessions.getCurrentUser` | возможные deleteRow по устаревшему номеру строки |
| `Auth.verifyOTP` | двойной submit кода → **повторное использование OTP**; параллельный вход с тем же device → **дубль девайс-сессии** |
| `Utils.cleanupStaleSessions` | deleteRow по съехавшим номерам во время чистки |

**Решение:** новый хелпер `Utils.withLock(fn, timeoutMs)` —
`LockService.getScriptLock()`, `tryLock` с таймаутом (дефолт 10 сек,
чистка — 30 сек), `releaseLock` в `finally`. При таймауте — понятная
ошибка `server_busy` (клиент предложит повторить), не вечное молчание.

**Три правила, соблюдённые в коде:**
1. Критические секции короткие — только чтения/записи таблиц.
   **Письмо (MailApp) в sendOTP отправляется ВНЕ замка** — иначе все
   входы встанут в очередь за почтой.
2. Замок **не реентерабельный**: `Sessions.createSession` и
   `sdpApplyDevicePolicy` своих замков НЕ берут — вызываются под
   замком `verifyOTP` (вложенный замок = взаимоблокировка).
3. Чтения перенесены ВНУТРЬ замков (прочитанное снаружи уже устарело).

## Проверка после деплоя (~2 минуты)

1. **Вход**: запросить OTP на свою почту, войти. В листе `sessions`
   новый токен — 32 символа из `0-9a-f` (раньше были заглавные буквы).
2. **Параллельный режим Task 346 жив**: войти моб + десктоп, выход из
   моба не выкидывает десктоп; последний выход сбрасывает
   `login_status` (как в тесте 08.09).
3. **Замок не мешает**: обычные действия (heartbeat каждые 5 мин,
   админ-панель) не выдают ошибок; `server_busy` видеть не должны
   (10 секунд ожидания — с огромным запасом).
4. В audit_log — обычные события (LOGIN_SUCCESS с device, LOGOUT c
   «another session stays active»). Новых типов событий НЕТ — замок
   тихий.

## Отказоустойчивость

| Ситуация | Поведение |
|---|---|
| `LockService` недоступен (ошибка) | исключение пробрасывается наружу как у любой мутации — клиент видит ошибку запроса; замок снят в `finally` |
| таймаут замка (10/30 сек) | ошибка `server_busy` — «повторите через несколько секунд»; данные НЕ тронуты |
| `Utilities.getUuid` недоступен | невозможно (встроенный GAS-сервис, как `SpreadsheetApp`) |
| ошибка внутри критической секции | замок снят (`finally`), ошибка проброшена — как до Task 348 |

## Откат

Заменить три файла на версии из коммита перед Task 348
(`git show <hash>:scripts/Utils.gs` и т.д.) → «New version». Старые
токены и сессии живут как жили — обратной миграции не требуется.
