# DEPLOY Task 347 — Автосчистка «заброшенных» сессий + Utils.gs в репозиторий

**Контекст (подтверждено 08.09.2026 в проде):** после фикса Task 346
последний logout всё ещё не сбрасывал `login_status`. По audit_log
(28.07–08.09) восстановлено: в листе `sessions` скопилось **37
строк-сирот** с почтой пользователя — входы без выхода, старый
сломанный logout их не удалял, а чистки трогали только сессии
УДАЛЁННЫХ пользователей. Фикс Task 346 честно видел «другую сессию»
и не сбрасывал статус. Пользователь вычистил строки руками — тест
пройден. Эта правка не даёт мусору копиться снова.

**Лечение:** новая функция `Utils.cleanupStaleSessions()` — удаляет
строки листа `sessions`, у которых `last_heartbeat` старше N дней
(config `STALE_SESSION_DAYS`, по умолчанию 30), и сбрасывает
`login_status` тем, у кого после чистки не осталось ни одной строки.
Вызывается из `hourlyCleanup` (часовой триггер уже настроен —
`setupTriggers`).

**Почему это не «истечение по времени» (заявка: сессии бессрочные):**
живое устройство бьёт heartbeat каждые 5 минут, поэтому
`last_heartbeat` активной сессии всегда свежий. Строка, молчавшая
месяц, — это удалённое приложение или очищенный браузер, а не живая
сессия.

**Состав активации — 2 правки (~5 минут):**
1. заменить содержимое файла `Utils.gs` целиком;
2. добавить **одну строку** в `Code.gs` → `hourlyCleanup`.

**НЕ требуется:** `sdpInit` (структура листов не меняется), правки
`Auth.gs` / `Sessions.gs` / `SessionsDevicePolicy.gs`, обновление
клиентов (PWA/десктопы). Триггер `hourlyCleanup` (раз в час) уже

## Шаг 4. Проверка (~1 час, пассивная; или 1 минута вручную)

1. Вариант «сразу»: в Apps Script Editor выбрать функцию
   **hourlyCleanup** в выпадающем списке → **Run** (▶).
   Вариант «как в проде»: дождаться ближайшего часового запуска
   триггера.
2. audit_log: события **`SESSION_CLEANUP_STALE`** — по одному на каждую
   удалённую строку (`last_heartbeat older than 30 days — session
   removed`); если у кого-то исчезли все сессии — ещё и
   **`LOGIN_STATUS_AUTO_RESET`**.
3. Лист `sessions`: строки со старым `last_heartbeat` (30+ дней)
   удалились; живые сессии (heartbeat свежий) НЕ тронуты.
4. Порог можно поменять: в лист `config` добавить строку
   `STALE_SESSION_DAYS` (колонки key/value) — например `90` для

**Признак «не применилось»:** запустили `hourlyCleanup` — в audit_log
нет `SESSION_CLEANUP_STALE`, старые строки в `sessions` на месте.
Значит: не опубликовали «Новая версия» (Шаг 3), или в `Utils.gs`
нет функции, или в `Code.gs` не добавлен вызов. Проверить порядок:
`Utils.gs` сохранить → `Code.gs` сохранить → «Новая версия».

**Как это работает / отказоустойчивость:**

| Ситуация | Поведение |
|---|---|
| Живая сессия (heartbeat каждые 5 мин) | `last_heartbeat` свежий → строка НЕ тронута |
| Строка молчит > 30 дней (приложение удалено, браузер очищен) | удаляется + `SESSION_CLEANUP_STALE` в audit_log |
| У пользователя после чистки не осталось строк | `login_status` → «вход не выполнен» + `LOGIN_STATUS_AUTO_RESET` (как самосинхронизация `Auth.sendOTP`) |
| Пользователь уже «вход не выполнен» | статус не перезаписывается (лишних записей нет) |
| Легаси-строка с пустым `user_id` (Task 37) | удаляется; статус её пользователя не трогаем — починит самосинхронизация при следующем входе |
| Пустой/невалидный `last_heartbeat` | считается «молчаливой» → строка удаляется (это очень старые строки) |
| Порог | конфиг `STALE_SESSION_DAYS` (по умолчанию 30) |
| Ошибка в одной из веток | `cleanupStaleSessions` не исключение-опасная: ошибки чтения листа остановят только её вызов, остальные чистки `hourlyCleanup` уже отработали |

**Откат:** убрать вызов из `hourlyCleanup` (или вернуть прежний
`Utils.gs`) → «Новая версия». Мусор снова будет копиться, но ничего
не сломается — функция ничего не меняет в логике входа/выхода.
