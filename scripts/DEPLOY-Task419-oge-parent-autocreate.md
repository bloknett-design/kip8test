# Task 419 — DEPLOY: особенность 9-ОГЭ + автосоздание новых сроков

Заявка: «У инструктажа по инструкции 9-ОГЭ есть особенность формирования
даты проведения, период 3 месяца, но инструктаж по этой инструкции включён в
Повторный инструктаж по рабочим инструкциям ОТ (6 месяцев)... при отметки
проведения инструктажей или проверки знаний, автоматически формировалась
новая запись в таблице "Инструктажи" с новым сроком проведения, в зависимости
от периодичности в таблице "Список_И_и_ПЗ"».

## Что сделано (коммит в main, SW kipia-test-v646)

### Сервер `scripts/WorkSchedule.gs`

1. **Связь «в составе»** — пункт «Списка_И_и_ПЗ» может ссылаться на
   пункт-родителя (столбец `в составе`; понимаются заголовки-синонимы
   «входит в» / «включён в» / «включен в», позиция любая — приём
   Task 402/403). Для заявки 9-ОГЭ связь **встроена в код**
   (`INSTR_DEFAULT_PARENT`): работает сразу, даже если столбца в листе
   нет; заполненный столбец ГЛАВНЕЕ встроенной связи (для других
   пунктов — только столбец).
2. **Автосоздание новых сроков при отметке выполнения**
   (`setTrainingDone`, выполнение = 1):
   - отмеченный пункт (периодичность N > 0) → новая запись того же
     пункта на **дата + N месяцев**, если в окне (дата; дата + N] ещё
     нет ни записи пункта, ни записи его РОДИТЕЛЯ;
   - **9-ОГЭ от общего инструктажа**: отметка общего → создаётся и
     самостоятельный 9-ОГЭ через **3 месяца**, и следующий общий
     через **6 месяцев** — чередование «по кругу из года в год»;
   - **покрытие**: незавершённые записи 9-ОГЭ с датой ДО даты
     отмеченного общего отмечаются выполненными автоматически
     («9-ОГЭ входит в его состав»);
   - снятие отметки ничего не создаёт и не удаляет;
   - записи вне «Списка_И_и_ПЗ» и разовые пункты (периодичность 0/пусто)
     — без автосоздания;
   - дата + N месяцев: день клампится к концу месяца (30.11 + 3 мес →
     28.02); id — глобальные по обоим листам (как addTraining).
3. Ответ `setTrainingDone` дополнительно несёт `created` (новые записи)
   и `updated` (покрытые) — клиент показывает их без перезагрузки.
4. `instrListInit`: шестой заголовок «в составе»; ячейка F3 (строка
   9-ОГЭ) заполняется названием родителя ТОЛЬКО если пуста — данные
   столбцов E/F при переинициализации не затираются.

### Клиент `index.html`

- `toggleTrainingDone`: записи из `created` кладутся в пулы без
  перезагрузки (`_INSTR_ALL` всегда; `_TRAININGS` — если год даты = году
  табеля), `updated` применяет отметки по id; тост перечисляет даты
  новых сроков («Отмечено выполнение — новые сроки: 16.12.2026,
  16.03.2027»).
- «след. срок» пункта-ребёнка считается от ПОСЛЕДНЕГО события — записи
  пункта ИЛИ его родителя: после общего инструктажа срок 9-ОГЭ = +3 мес,
  а не «просрочено» от старой собственной записи.
- Встроенный эталон `_INSTR_CANON` несёт связь 9-ОГЭ → общий.

## СЕРВЕРНЫЙ ШАГ ПОЛЬЗОВАТЕЛЯ (обязательно)

1. В проекте Apps Script (табель_КИП_ИОС) полностью замените содержимое
   файла `WorkSchedule.gs` на новый `scripts/WorkSchedule.gs` из репо.
2. `Code.gs` НЕ менялся (маршрут `setTrainingDone` уже есть с Task 418).
3. Разверните новую версию: **Deploy → Manage deployments → ✏ →
   Version: New version → Deploy**.
4. НЕ обязательно (по желанию): запустить `instrListInit` — добавит
   заголовок «в составе» и связь в F3; автосоздание работает и без
   этого (встроенная связь). Для ДРУГИХ пунктов-детей (если появятся)
   заполните столбец «в составе» вручную.

## Как проверить после обновления сервера

1. Откройте карточку работника → блок «Повторные инструктажи и
   периодическая проверка знаний» → галочка у записи общего
   инструктажа: появляются новые записи (9-ОГЭ +3 мес; общий +6 мес),
   тост со сроками; старый незакрытый 9-ОГЭ отмечается сам.
2. Галочка у самостоятельного 9-ОГЭ: если общий уже запланирован на +3
   мес — новая запись НЕ создаётся (общий покрывает 9-ОГЭ).
3. Проверки знаний (12 мес): отметка → новая запись +12 мес.
