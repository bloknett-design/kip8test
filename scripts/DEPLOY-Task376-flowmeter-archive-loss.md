# DEPLOY Task 376 — расходомеры: потерянная строка архива (meters записан, архив нет)

**Дата:** 2026-09-17
**Заявка пользователя:**
> «Есть замечание по разделу Расходомеры хозрасчётные, при вводе новых данных расходов,
> в последнем расходомере №12 введённые новые данные записались на сервер в
> hozraschet_meters, а в архиве на hozraschet_archive не записались, в чём может быть
> причина, проверь.»

## 1. Диагноз (подтверждён кодом)

`Flowmeter.gs → updateReading` работает в два шага:

1. **Сначала** пишет meters-строку (~10 прямых `setValue`, БЕЗ замка).
2. **Только потом** вызывает `FlowmeterArchive.appendToArchive` — а тот обёрнут в
   `catch`, глотающий **любую** ошибку как «non-critical», и `updateReading` всё равно
   возвращает `ok: true`.

Внутри `appendToArchive` запись идёт под `Utils.withLock` → `tryLock(10000)` —
замок скрипта Apps Script **один на все выполнения**. При вводе всех 12 расходомеров
подряд (или параллельных beacon-доставках при закрытии приложения) очередь на замок
длинная, и **последний в очереди — №12 — упирался в таймаут 10 c** → `server_busy` →
глотался как «non-critical» → **строка архива терялась при записанном meters**.
Тот же эффект дают транзиентные ошибки квоты Sheets («Service invoked too many
times»), прерывания выполнения.

Клиент получал `ok:true` → тост «Показания сохранены» → запись удалялась из outbox →
**повторной доставки не было никогда**. Усилитель: дедуп `_flushOutbox` для day-записей
сверялся ТОЛЬКО с `flowmeter.list` (meters) — раз meters совпал, запись из outbox
удалялась без проверки архива (дыра становилась постоянной).

## 2. Исправление

### Сервер (Apps Script) — `FlowmeterArchive.gs` + `Flowmeter.gs`

| Что | Как |
|---|---|
| Ретраи записи архива | `appendToArchive`: **3 попытки** захвата замка (10 c + 4 c + 4 c, пауза 1 c) — транзиент очереди/квоты рассасывается за секунды. После последней неудачи исключение **ПЕРЕБРАСЫВАЕТСЯ** (не глотается). «Дубль» (строка уже в архиве, правила Task 366/375) ошибкой НЕ считается |
| Честный ответ | `updateReading` при сбое архива возвращает `ok:false, error:'archive_write_failed'` с пояснением «Показания сохранены, но запись в архив временно не удалась — она будет отправлена повторно автоматически». meters УЖЕ записан — повторная доставка идемпотентна, серверный дедуп не даст дубль строки |
| Периодические записи | `_writePeriodEntry`: тот же стабильный код `archive_write_failed` (архив — единственное хранилище записи за месяц) |

### Клиент (PWA)

| № | Что | Как |
|---|---|---|
| 1 | `archive_write_failed` — не «окончательный отказ» | `_outboxIsPermanentError`: код освобождён от удаления (как `server_busy`) — запись будет ретраиться |
| 2 | Ветки честной обработки | `_sendUpdateReading` / `_submitPeriodEntry`: запись ОСТАЁТСЯ в outbox (state `retry`), ретрай-таймер, честный тост «…отправим повторно автоматически» (не «нет связи») |
| 3 | **Дедуп флаша по архиву** | `_flushOutbox` day-дедуп: meters-совпадение — только КАНДИДАТ на «доставлено»; финальное подтверждение — строка в архиве (`entryType + dateCurr + curr`, запрос `flowmeter.archive` на расходомер). Нет строки → запись уходит повторно (meters перезапишется идемпотентно, дедуп сервера не даст дубль) |
| 4 | Ретрай-таймер после флаша | `finish()`: если после флаша что-то осталось (сеть/`server_busy`/`archive_write_failed`) — сам планирует ретрай с бэкоффом (раньше ждал только online/visibility/заход в раздел) |
