## Заявка пользователя

> «В хозрасчётах №3 и №11, в форме ввода показаний должен выбираться
> период из двух дат определяющих период, и значения по умолчанию
> в форме должны стоять даты за предыдущую календарную неделю.
> Также с хозрасчётом №9, только период месяц. Еженедельные: красный,
> когда календарная неделя (пн–вс) прошла; зелёный — когда данные
> этой недели введены; снова красный, когда текущая (новая) календарная
> неделя (пн–вс) прошла, пока не введут за неё данные. Ежемесячные:
> красный, когда календарный месяц данных прошёл; зелёный — когда
> данные за этот месяц введены; снова красный, когда (новый) текущий
> календарный месяц прошел, пока не введут данные за его период.»

## Что изменилось (только клиент index.html + sw.js)

### 1. Форма ввода показаний — период из двух дат
- **№3, №11 (Еженедельно) и №9 (Ежемесячно)**: поля «Период с … по …»
  (второе поле `#flowInputDateEnd`, ранее использовалось только для
  «расхода за месяц» Хозрасчёта №1).
- Дефолты нового ввода: **границы прошедшей календарной недели**
  (пн–вс, новый хелпер `flowPrevWeekRange`) / **прошлого календарного
  месяца** (`flowPrevMonthRange`). Пустые поля при сохранении
  заполняются теми же дефолтами.
- Правка (окно 1 ч): поля предзаполнены датами записи
  (`datePrev` → «с», `dateCurr` → «по»).
- Hard-проверка «конец раньше начала» — тост, запись не уходит
  (зеркало серверной DATE_INCONSISTENT и ветки №1).
- Классификация — по периоду из таблицы (`_isWeeklyMeter` /
  `_isMonthlyMeter`, регэкспы Task 367: «Еженед.», «Ежемес.»,
  «N раз в неделю/месяц»); №1 исключён (свой chips-флоу).
- Отправка — **обычным маршрутом `flowmeter.updateReading`**:
  `datePrev` = «Период с», `dateCurr` = «по». Сервер пишет обе даты
  в meters-строку (колонки D/E) и в архив; расход = curr − prev
  за выбранный период. **Серверные скрипты НЕ менялись.**

### 2. Красный «пора вводить» — по ЗАКРЫТЫМ календарным периодам
Ссылка — последний ПОЛНОСТЬЮ ЗАКРЫТЫЙ период:
- **Еженедельно**: неделя пн–вс, закрывшаяся в прошлое воскресенье
  (в понедельник 00:00 — уже новая закрытая неделя).
  Зелёный — период последних данных `[datePrev … dateCurr]` накрывает
  (пересекает) закрытую неделю; красный — закрытая неделя без данных;
  снова красный с закрытием следующей недели, пока не введут за неё.
  Точечное показание, снятое в течение закрытой недели, — тоже «данные
  этой недели» (пересечения достаточно). Legacy-записи без `datePrev`
  считаются точечными `[dateCurr … dateCurr]`.
- **Ежемесячно**: аналогично по календарному месяцу (1-е … последнее
  число; закрытие — 1-е число следующего месяца 00:00).
- Хелпер `_recordCoversPeriod`; суточная логика (6:00, Task 365)
  не тронута.

### 3. Подписи-диапазоны
- Карточки списка и детальная карточка: «Последние показания
  **за 07.09–13.09.2026 г.**» (через `flowWeekRangeLabel`; точечная
  legacy-запись остаётся одной датой).
- Хронология показаний: записи недельных/месячных расходомеров —
  диапазон дат записи (класс `flow-archive-date-range`, БЕЗ бейджа
  «нед/мес» — это показания, а не агрегат «расход за неделю/месяц»
  Хозрасчёта №1).

## Серверные действия

**НЕ ТРЕБУЮТСЯ.** Все правки клиентские; серверный маршрут
`flowmeter.updateReading` уже пишет `payload.datePrev`/`payload.dateCurr`
в meters-строку (D/E) и архив как есть. Правки Apps Script из Task 366
(дедуп архива `FlowmeterArchive.gs` + «Новая версия») остаются
актуальными отдельно — они не связаны с Task 368.
